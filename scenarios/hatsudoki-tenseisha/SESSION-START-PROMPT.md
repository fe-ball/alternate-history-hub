# 発動機転生者 — セッション開始テキスト

発動機転生者世界線の議論を再開する。

このシナリオでは、現在の製品・機体・性能表を静的な完成状態として読むのではなく、**その時点までに何を知り、何を試し、何を作り、何を学び、その結果として次の要求・研究枝・製品計画がどう発生したか**を最優先で追うこと。

現在値の把握だけでなく、技術・組織・軍要求・会社戦略が時系列で発展する過程を正本の一部として扱う。

## 2. 世界線の最上位前提

主人公は現代の自動車用ガソリンエンジン技術者である転生者であり、未来知識を持つ。
ただし万能知識ではない。

主人公が無料に近く得られるのは主として、

- 正しい方式・設計枝の選択
- 後世に失敗すると分かっている枝の回避
- 何を測るべきか
- failure mode の先取り
- 実験計画・DOE
- 設計空間探索
- 量産設計・工程設計
- SPC・品質管理・変更管理
- 後世に有効と分かっている技術を、現地条件で成立可能な形へ早期提案する能力
- 長時間を要する研究・耐久・工程成熟の時計を、必要性が見える場合に早く開始する能力

である。

主人公は、

- 存在しない材料
- 当時作れない合金・熱処理
- 加工不能な形状
- まだ存在しない工作機械
- 未測定係数
- 実際に回していない長時間耐久
- 疲労・摩耗・腐食の実時間
- 未成熟な量産歩留まり
- 軍の予算
- 工場能力
- 機体工場
- 搭乗員・整備員
- 燃料・補給網

を無料で生成しない。

## 3. 史実年代は能力上限ではない

史実の発明年、初飛行年、制式年、量産年を能力上限として使わない。

「史実より早い」「当時として高度すぎる」「日本ではまだ存在しなかった」「数字が強すぎる」という理由だけで性能や開発時期を史実へ巻き戻してはならない。

技術を成立させられない、または遅らせる場合は、

- 材料・熱処理
- 加工・公差
- 計測
- 試験設備
- flow / thermal / vibration map
- fatigue / wear / corrosion
- endurance duration
- 重量・容積
- 搭載
- supplier capacity
- 量産歩留まり
- 整備・兵站

等の具体的な未払いゲートを示す。

逆に物理・産業・組織上のゲートが払われているなら、史実から離れた結果であること自体を弱体化理由としない。

## 4. idea gate と physical gate

すべての新技術・新製品について、

**idea / answer-selection gate**
と
**physical / industrial gate**

を分ける。

主人公の未来知識は前者を非常に強く開く。
しかし後者は現地で払う。

「正解を知っている」ことと、「その正解を量産可能な航空発動機として完成させている」ことを同一視しない。

## 5. future-CAD benchmark

future-CAD benchmark は未来工場の召喚ではない。

対象年の日本で使える、

- 材料・燃料
- 工作機械
- 工員・技能
- 計測器
- 試験設備
- 工場・電力
- 資金
- supplier
- qualificationに必要な時間

を固定する。

その条件で、現代級の設計知識・解析・生産技術・故障知識を持つ専門家集団が作れる最善の設計、工程、公差、検査、試験計画、failure-mode一覧、trade study を100% benchmarkとする。

## 6. Gp / Gd / Gq、L0–L4、余裕通貨

能力を一つの倍率にしない。

- Gp: performance gain capture
- Gd: development gain capture
- Gq: quality gain capture

Gpを単純な出力倍率にしない。

問題クラスもL0–L4に分離する。

- L0: 方式選択・系列構成。未来知識が極めて強く効く
- L1: 基本寸法・CR・減速比・基本熱収支等
- L2: port、混合分配、点火、過給機map、冷却ΔP等。試験が必要
- L3: 捩り振動、動弁、熱変形、過渡等。計装・反復が必要
- L4: 疲労、摩耗、腐食、焼付き、軸受寿命、量産歩留まり等。実時間を大きく踏み倒せない

技術項目ごとの「+3%」「+5%」を単純加算せず、

- knock
- filling
- thermal
- mechanical / rpm
- friction
- weight
- cooling drag
- exhaust energy
- life
- production variance

等の物理財布へ一度集約し、そこから peak power、離昇、30分定格、常用最大、巡航、高空出力、燃料耐性、寿命、重量、冷却抗力、BSFC、量産再現性、将来成長へ配分する。

同じ余裕を二重計上しない。

## 7. 生産・試験・品質を設計性能と同格に扱う

当時日本を「ヤスリで一個ずつ仕上げる未近代工業」とみなさない。

史実日本の近代的工作・治具・検査・量産能力を基礎とし、主人公の現代自動車技術者としての強みを、

- DFM
- tolerance allocation
- datum / setup design
- fixture strategy
- gauges
- SPC / process capability
- change control
- supplier quality
- failure feedback
- standard work
- test planning

の早期体系化に置く。

設計性能、生産技術、工程設計、試験能力、品質管理を同格の能力軸として扱う。

## 8. 未来視の有限性は「その先を考えるな」ではない

主人公の未来視には時間規律がある。

甲を設計する時点では乙を強く見通してよい。
甲はO2へ進むための共通気筒・燃焼・弁・リング・油・冷却・加工工程を意識して設計してよい。

ただし甲の時点では、

- 尾張発動機がどこまで大会社になるか
- 軍がどこまで信頼するか
- どの程度の資金・工場・試験設備を得るか
- 将来の軍要求がどの形で来るか

が見えきっていない。

したがって甲の時点から誉・ハ43級、1944年要求までを一つの気筒・製品仕様へ固定しない。
これは主人公がその先を知らないからではなく、**会社と要求の不確実性が大きく、そこまで製品仕様へ固定する合理性がないから**である。

乙の開発段階では事情が変わる。

乙/O2は寿・光世代に勝つ主力商品を意図し、とくに寿に対して性能で明確な優位を狙う。ただし重量差があるため、寿との比較では用途によって選択が残りうる。
さらに乙の発展系列は、その後数年の栄級要求を明確に上回ることを設計上の成長目標とする。

したがって乙の開発・成熟と並行して、

- 乙小改
- 高度性能向上
- 過給機発展
- 回転数・BMEP上昇余地
- 92oct利用
- 長時間定格型
- post-O2 architecture
- 気筒数増加
- 新気筒
- より大型の次系列

等のtrade studyが行われること自体は自然である。

**「乙が完成してから初めて次を考える」という直列史にしてはならない。**

ただし、考えていること、paper study、物理研究、正式製品計画、軍要求、量産を同一視しない。

## 9. 発展は並行工程

製品史を、

「甲完成 → 乙を考える → 乙完成 → 丙を考える」

という直列工程にしない。

現行品量産、故障改修、次期改良型、次世代architecture study、軍向け提案、社内基礎研究は重なって存在しうる。

各研究枝について少なくとも、

1. idea / paper study
2. trade study
3. 人員・予算付与
4. rig / coupon / single-cylinder / mock-up
5. prototype
6. ground / endurance test
7. flight installation
8. qualification
9. military requirement / company proposal
10. adoption
11. serial production
12. allocation / serviceability / unit deployment

を区別する。

未来知識で思いつけるからといって、すべての枝が最初から物理的な開発時計を持つことにはしない。

## 10. 次期製品の起点は三種類

### COMPANY-ORIGIN

主人公・尾張発動機が、

- 未来需要を予見した
- O2の成長限界を考えた
- 将来の高出力帯へ先行投資する価値がある
- 他社より先に市場を作れる

等の理由から自主研究を開始する。

軍要求前にpaper study、単気筒、rig、mock-up、社有試験機等が存在してよい。
ただし軍採用、予算、量産、部隊配備は自動的には付いてこない。

### MILITARY-ORIGIN

O1/O2で信頼を獲得した結果、陸海軍が尾張発動機へ、

- より高い高度定格
- より大きな連続出力
- より小径・軽量
- 双発機用の長時間出力
- 次期戦闘機用の上昇力
- 新しい燃料条件

等の要求を出し、それを起点に新計画が正式化する。

### MIXED

会社が既に持つ研究枝へ軍要求が接続し、正式計画へ昇格する。

「軍が要求するまで何も考えない」「主人公が未来を知っているから軍要求なしで全部量産する」の両極端を避ける。

## 11. 要求 → 試作 → 実測 → 新要求

開発史の基本ループを、

**要求・仮説 → 設計 → rig / prototype → 実測 → failure / margin の発見 → 要求修正 → 次の枝**

とする。

後続製品を後世の完成形から逆算して一度に完成させない。

一方、未来知識によって、

- 最初の方式選択
- 試験項目
- instrumentation
- failure-mode想定
- 捨てるべき枝

は史実より大幅に改善してよい。

実測は未来知識の答え合わせだけではない。
予想外の材料品質、加工ばらつき、冷却分布、振動、機体搭載、軍運用結果は新しい要求を生む。

## 12. 長い時計の先払い

疲労、摩耗、腐食、軸受、冷却、過給機、工程能力、field-return、専門技術者育成等は実時間を要する。

ただし未来知識により必要性が早く分かり、主人公や会社に合理的理由・人員・資金があれば、その時計を史実より早く開始してよい。

後年その技術が必要になった時点から時計をゼロスタートさせない。

一方、未来に必要になることを知っているだけでは時計は進まない。

必ず、

- 研究決定
- 予算
- 担当者
- rig
- 試験片
- 試作
- 運転時間

等の具体的な開始イベントを置く。

## 13. 獲得済み能力を巻き戻さない

一度、日時を持つ開発・試験・量産・組織学習によって獲得した能力は、次製品へ移っただけで史実日本の平均へ戻らない。

例えば、

- 試験設備
- 動力計・計装
- failure taxonomy
- 設計手順
- 公差設計
- 治具・gauge
- SPC
- heat-treatment know-how
- supplier管理
- teardown / field-return解析
- 技術者集団
- 燃焼・リング・潤滑・冷却のデータ

は、因果的に共通なら引き継ぐ。

新製品で時計をゼロへ戻すのは、本当に新しい材料、形状、負荷、工程、機構、使用条件等だけである。

能力を低下させる場合は、設備破壊、人材喪失、材料品質低下、試験時間不足、supplier崩壊等の因果を示す。

## 14. capability / procurement / deployment / effect を分離

最低でも、

`technical capability`
→ `company research / military requirement`
→ `physical prototype`
→ `qualification`
→ `adoption`
→ `serial production`
→ `allocation`
→ `serviceability`
→ `unit deployment`
→ `tactical effect`
→ `operational effect`
→ `strategic effect`

を別々に確認する。

これは固定された唯一の順序ではない。
会社試作が軍要求より先に来てもよいし、軍要求が試作より先でもよい。
ただし後段の主張をする場合、必要な中間ゲートを飛ばさない。

## 15. 発動機・搭載・定格を分離する

監査名 甲/乙、社内型式 O1/O2、世界内名称 旭/暁を混同しない。

O1/旭、O2/暁について現authorityから、

- bore × stroke
- displacement
- dry mass
- diameter
- fuel
- ratings
- thermal condition
- TBO / production maturity

を取得する。

87oct正規定格と92oct特認を分離する。

公称定格を「最悪条件最低保証」として大幅に寝かせず、指定燃料・吸気条件・rpm/boost・温度条件で受領・耐久試験を通した使用上限として扱う。

離昇、30分定格、常用最大、巡航を機体計算で使い分ける。

exhaust thrust、cooling drag、propeller efficiency、intake loss、cowl dragをshaft hpへ混ぜない。

O2の30分定格はinstallationの冷却差圧・CHT条件に依存し、高速単葉と低速複葉で利用可能出力が異なる。

prototype best、公称定格、量産中央値、量産ばらつき、部隊で実際に使える出力を混同しない。

## 16. 主人公個人と組織能力、技術伝播を分ける

主人公本人が知っていることと、尾張発動機という組織が再現できることを分ける。

主人公が一度、

- 試験体系
- 設計手順
- QC
- failure analysis
- 工程設計
- 文書化
- gauge / fixture
- supplier管理

として組織へ移したものは、本人が毎回直接設計しなくても継続できる。

一方、主人公しか知らない未文書化の未来知識を社員全員へ自動コピーしない。

軍、航空廠、機体メーカー、他発動機メーカーへの伝播も、

- 実機
- 図面
- interface specification
- 試験記録
- 技術者
- joint test
- supplier
- license
- field feedback

等の具体的経路を必要とする。

## 17. 後年結果の逆流を禁止

後に成功した製品、量産値、戦訓、部隊評価があるからといって、その情報を早期checkpointの人物が知っていることにはしない。

分析者として後年との因果整合性を監査してよいが、actor knowledgeへ逆流させない。

特に、

「後にこの型が成功するから1933年から正式計画だった」
「後に誉級が必要になるから1932年に仕様を完全固定した」

という処理をしない。

ただし主人公自身が持つ未来知識の範囲は、本シナリオ固有の有限未来視規律に従う。

## 18. 機体側も同じ発展規律を使う

機体・発動機の選択肢を「未来知識で思いつけるから最初から全部存在する」としない。

海軍・陸軍それぞれについて、

要求
→ 試作
→ 比較
→ 実測
→ doctrine / requirement変化
→ 次期機

を追う。

史実相当機は史実の試作番号・略符号・制式名称を優先し、発動機換装だけで新しい機体番号を作らない。

完全新要求・独立設計として史実相当性を失った場合のみ新番号を検討する。

海軍と陸軍が同じ技術へ独立収斂する場合と、実機・図面・試験結果・技術者等を通じて学習する場合を区別する。

## 20. O2B / post-O2を扱うときの必須監査

現在のO2Bや次系列の仕様をいきなり決めない。

まず1931～1937前半程度を時系列で、

- O2そのものの状態
- O2発展型についてその時点で分かっていること
- post-O2について社内で考えていること
- どの枝に人員・予算・rigが付いたか
- 軍が知っていること
- 軍から来ている要求
- 実測で新しく分かったこと
- まだ決められないこと

に分けて再構築する。

特に、

**「現在のO2Bを説明する前に、なぜO2Bが発生したのか」**
**「次系列の仕様を決める前に、いつ誰が何を理由に次系列研究を開始したのか」**

を必ず確認する。

仮称丙以降については、会社都合の自主研究、O2で信頼を得た軍からの要求、その両者が接続するmixed routeを比較する。

「誉キラー」等の後世比較は分析用の便宜語として使ってよいが、当時の正式要求や唯一の会社目的へ自動変換しない。

## 21. 状態ラベルと不確実性

- CLOSED: 今後の入力として採用済み
- PROVISIONAL: 現在の最良案だが監査で変わりうる
- OPEN: 未決
- REFERENCE: 比較・旧体系

GitHubに存在することだけを理由にCLOSED/CANONへ昇格させない。

証拠や物理監査が不足する場合、史実値へ自動復帰しない。

- bandを広げる
- PROVISIONALのままにする
- OPENとして残す
- 次に閉じるべきgateを示す

のいずれかとする。

細部を際限なく台帳化せず、まず major common bottleneck、engine / airframe / installation feasibility、qualification / production repeatability、serviceability / allocation を監査する。
propeller、carburetor、magneto、bearing、supplier等の詳細台帳は、それが実際に律速すると分かった場合に開く。

## 22. 過去資料との監査

過去資料との矛盾、旧値残存、二重計上、古いauthority、manifest不整合、参照切れがあれば抽出する。

意味を変えない範囲で整理・修正してよい。
ただし未承認事項や暫定推論をCLOSED/CANONへ勝手に昇格させない。

特に旧135×152系列、旧乙/丙定格、旧機体性能、旧生産・戦史をリランチ後へ自動継承しない。

少なくとも、

## 24. GitHubへの反映

会話中の推論・暫定案を自動でGitHubへ書かない。

ユーザーが、

- 「GitHubに投げろ」
- 「ここまでGitHub反映」
- 「GitHubへ編入」

等と明示した場合のみ永続化する。

その際、authority、canonical clock、clock_state、frontier、import scope等が変化するなら `scenarios.yaml` も同じ処理で更新する。

未承認事項・暫定推論を勝手にCLOSED/CANONへ昇格させない。
